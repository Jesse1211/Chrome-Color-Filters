# 设计:用 GitHub Pages 发布灰阶研究报告(第一阶段)

日期:2026-11-26
状态:待批准

## 意图与动机

仓库里的 `reports/gray/index.html` 是一份做完了的双语研究报告,目前只能在本地
打开。把它发布到 GitHub Pages,等于给这份报告一个可以直接发给别人的网址,
而不是让人去 clone 仓库。

发布用 GitHub Actions 自动完成 —— 推送即上线,不需要手工操作。

## 分三步走,本设计只覆盖第一步

用户明确要求按顺序推进,一步跑通再做下一步:

1. **(本设计)** Pages 把研究报告发布在站点根路径。
2. 发布扩展本身(落地页 / 安装说明)。
3. 把两者互相链接起来。

第二、三步各自重新设计,本文不预先决定它们的形态。

## 目标

- 研究报告可以通过 `https://jesse1211.github.io/Chrome-Gray-Scaller/` 访问。
- 推送到 `main` 且改动了报告文件时,自动重新发布。
- 可以手工触发发布(`workflow_dispatch`),不必靠一次假的提交。
- 中英文切换在线上必须可用。

## 非目标

- 不发布扩展的落地页(第二步)。
- 不发布 `docs/` 下的门禁证据、ADR、spike 记录。
- 不碰 `entrypoints/popup/index.html`(扩展源码)、`build/chrome-mv3/popup.html`
  (已被 gitignore 的构建产物)、`docs/design/popup-mockup.html`(设计稿)、
  `docs/T0-spike/spike-code/fixture/page.html`(测试夹具)—— 这四个 HTML 都不是
  给读者看的。
- 不自定义域名。

## 反目标(即使技术上跑通了,出现这些也算失败)

- 线上页面的英文切换坏掉,但中文看起来正常 —— 这种缺陷不会报错,只会静默少掉一半内容。
- 为了发布一个静态页面,让扩展的测试套件成为上线的卡点:改一个错别字却被
  一个无关的测试失败挡住。
- 把生成的产物提交进 git 仓库。

## 约束

- **(2026-11-26 更正)** 设计初稿写的是「`index.html` 通过相对路径 fetch 取
  同目录的 `i18n.json`,因此两者必须保持同级」。**这是错的,已核实。**
  实际情况:英译词典在构建时已经**内联**进 `index.html`(第 1374 行
  `var __I18N__={...}`),语言切换纯在内存里做,偏好存 `localStorage`。
  整个 `index.html` 里**没有任何相对路径引用** —— 唯一的外部资源是
  Google Fonts 的样式表(绝对 URL)。核实方法:把 `index.html` 单独复制到
  空目录,`grep` 相对 `src`/`href` 得零结果。
  **影响:** `i18n.json` 是构建期的**源文件**,不是运行期依赖;部署产物
  只需要 `index.html` 一个文件。这反而消除了「摊平目录会静默弄坏英文」
  这个风险 —— 原来的反目标因此不再是本阶段的风险点,但验收仍然要实际
  点一次英文切换(理由见下)。
- 仓库此前没有 `.github/` 目录,这是第一个 workflow。
- Pages 的来源需要在仓库设置里一次性选为 "GitHub Actions"(仓库设置,不是代码,
  需要用户手动点一次)。

## 可选方案

**方案 A — Actions 原生 Pages 部署(已选定)**
用 `actions/upload-pages-artifact` + `actions/deploy-pages`,把 `reports/gray/`
作为构建产物交给 Pages。没有 `gh-pages` 分支,没有被提交的构建产物,仓库结构
保持原样。

**方案 B — `gh-pages` 分支部署**
由 workflow 把站点推到一个 `gh-pages` 分支,Pages 去服务那个分支。可行,但要
往仓库里加一个装着生成内容的分支,还要信任一个第三方 action。它唯一的真实好处
是「部署历史可以当成 commit 来浏览」,而发布单页用不上这个。

**选定 A,理由:** 这是 GitHub 当前的第一方路径,生成文件完全不进 git;对一个
静态目录来说,B 没有任何额外收益。

## 决定了的实现细节

- **工作流文件:** `.github/workflows/pages.yml`
- **触发条件:** `push` 到 `main` 且路径命中 `reports/gray/**`,以及
  `workflow_dispatch` 手工触发。
- **不设代码门禁。** 报告不依赖扩展能否编译,所以 `compile` / `test` / `lint`
  不作为本次发布的前置条件。这三个检查确实还没有被任何 CI 跑过,但它们属于
  扩展,和第二步一起作为独立的 workflow 引入 —— 这样两件事互不牵连,正好对应
  路径过滤的意图。(这一条是我的判断,用户只选了方案 A。)
- **产物内容:** 整个 `reports/gray/` 目录原样上传。这样做不是因为必须
  (`index.html` 自给自足,单独一个文件就能跑),而是因为「上传一个目录」
  比「挑文件」更简单、也不会在报告未来真的新增资源时悄悄漏掉。
  代价是 `i18n.json`(52 KB 构建期源文件)会一起上线 —— 可接受:它本就在
  公开仓库里,不是敏感内容。
- **`.nojekyll`:** 加上。Pages 默认会跑 Jekyll 处理,对这个页面毫无用处,
  只是多一个变量。
- **权限:** workflow 用 `permissions: pages: write, id-token: write,
  contents: read`,并发组设为 `pages` 且不取消进行中的部署。

## 留给实现者的部分

- action 的具体版本号(用各自当前的主版本标签)。
- job 的拆分方式(单 job 或 build/deploy 两个 job,都可接受)。

## 验收

- workflow 在 GitHub 上跑成功。
- 访问站点根路径能看到报告。
- 在线上点语言切换,英文内容确实出现。词典既然是内联的,这一条理论上
  不可能因为部署方式而坏掉,但仍然要实际点一次:它同时验证了页面的
  内联脚本在 Pages 上没有被任何处理环节改动过(这正是加 `.nojekyll`
  要防的那类问题)。
